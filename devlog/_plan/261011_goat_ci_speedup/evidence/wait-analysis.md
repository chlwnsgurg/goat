# SSH tunnel test wall time

Scope: `packages/ssh/src/tunnel.ts`, `packages/ssh/src/tunnel.test.ts`, and `/tmp/goat-ci/ci-test-durations.tsv`. CI reports 1221.110 s for 325 tests; 80 entries at >=5 s sum to 837.922 s (68.6%). These are **measured CI durations**, not a profile of individual subprocesses. One isolated local run of `manager consumes its startup decision once: busy` passed in 12.87 s total (13.06 s tool wall time; CI: 24.784 s). No repository files were changed.

## Families and changes

`P` below means real top-level processes directly visible in the fixture, not all children of its generated shell. `makeProtocolFixture` starts `mkfifo`, a native Node script generator, `tar`, and (for `live: true`) one Node server: **P=3 cold / 4 live before the call** (`tunnel.test.ts:3496-3509,3533-3587`). Each `f.run` starts at least one real remote shell (`tunnel.test.ts:3641-3692`), which in turn starts several Node protocol/CLI helpers (`tunnel.ts:708-745,900-952`). This is a lower bound; subprocess counts and their per-process duration were not profiled. A one-call live case therefore has P>=5; a two-call case P>=6. The repeated candidate/live rechecks and ownership `ps`/hash subprocesses explain why non-timeout cases are already ~8 s on CI (`tunnel.ts:1515-1532,900-952,970-1065`).

## Ordering and unresolved points

1. The cleanest immediate gain is the 16-spawn byte test, followed by the one 5 s lock test. Both can change test execution without altering production script bytes.
2. The large protocol family needs subprocess timing before claiming a timeout is dominant. Add temporary timing around `remoteSpawn` in the fixture (`tunnel.test.ts:3641-3692`) and, if needed, trace child commands from the generated shell. The current TSV cannot apportion Node startup, `ps`, hash, or `wait_for_pid_exit` precisely.
3. If a genuinely expected timeout case is discovered, retain the timeout behavior and inject a smaller test value. Do not replace a failure with immediate mock success. For local HTTP, the existing `waitForHttpReady` parameters suffice (`tunnel.ts:2205-2217`); for generated remote scripts, use an optional timing argument whose omitted values reproduce today's exact bytes (`tunnel.ts:1387-1407,1484-1486,1906`).
