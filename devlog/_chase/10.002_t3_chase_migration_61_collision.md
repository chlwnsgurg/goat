# 10.002 — 마이그레이션 id 61 충돌

> 사이클: 261012 · 상태: ⛔ needs decision · P0 · GOAT 영역: G7
> upstream: `1f6df6bf1` (#18124) `061_PullRequestReviewGuides` · GOAT: `c96310a1a` `061_ServerActivityIndexes`

## 무엇이 다른가

- GOAT dev `apps/server/src/persistence/Migrations.ts`는 `[61, "ServerActivityIndexes", ...]`, upstream
  main은 `[61, "PullRequestReviewGuides", ...]`이다. upstream 61은 `pull_request_review_guides` 테이블을
  `CREATE TABLE IF NOT EXISTS`로 만든다.
- migrator는 기록된 최대 id 이하를 건너뛴다 (`.repos/effect-smol/packages/effect/src/sql/Migrator.ts:258`).
  `c96310a1a` 이후 GOAT 빌드로 한 번이라도 띄운 DB는 61을 GOAT 이름으로 기록했으므로, 그대로 머지하면
  `pull_request_review_guides`가 만들어지지 않는다. upstream의 guided review(`1f6df6bf1`)와 review guide MCP
  도구(`18656a340`)가 실행 중에 테이블 없음으로 실패한다.
- GOAT 61은 다시 실행하면 실패한다. `ALTER TABLE ... ADD COLUMN has_pending_background_work`와 `IF NOT EXISTS`
  없는 `CREATE INDEX` 여섯 개다. 번호만 62로 옮기면 이미 적용된 DB에서 컬럼 중복으로 깨진다.
- 이미 GOAT 61을 기록한 DB의 범위(개발자 데스크톱, SSH 원격 런타임)는 확인하지 않았다.

## 선택지

| 안  | 내용                                                                                                                                                                                                                                                                                                                                                       | 비용과 위험                                                                   |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| A   | upstream이 61을 갖고 GOAT activity는 62로 옮기며 멱등하게 다시 쓴다 (컬럼 존재 확인, `CREATE INDEX IF NOT EXISTS`). migrator 앞에서 도는 reconcile 단계(`reconcileV2PreviewMigration`과 같은 자리)가 `(61, ServerActivityIndexes)` 기록을 보면 upstream 61 본문을 실행하고 기록을 `(61, PullRequestReviewGuides)`, `(62, ServerActivityIndexes)`로 고친다. | reconcile 함수 하나와 테스트. 이후 사이클에서 GOAT id가 다시 밀려도 같은 패턴 |
| B   | GOAT 61을 유지하고 upstream 61을 62로 옮긴다.                                                                                                                                                                                                                                                                                                              | 이후 upstream 마이그레이션 번호가 GOAT에서 계속 1씩 어긋나 매 사이클 재번호   |
| C   | activity 인덱스를 upstream에 PR로 올려 GOAT 전용 마이그레이션을 없앤다.                                                                                                                                                                                                                                                                                    | 근본 해결이지만 수락 시점을 모른다. 그동안 A가 필요                           |

권장은 A이고, 장기적으로 C를 시도한다.

## 결정이 필요한 이유

사용자 DB의 스키마와 마이그레이션 기록을 바꾸는 선택이라 [README](./README.md) 규칙 3에 따라 사람이 정한다.

## 닫는 근거

- GOAT 61이 기록된 DB를 만든 뒤 마이그레이션하면 `pull_request_review_guides`가 생기고 기록이 61과 62로
  정리되는 테스트, 새 DB 경로 테스트.
